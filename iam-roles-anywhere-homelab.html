IAM Roles Anywhere

How a workload running outside AWS can use an X.509 certificate to obtain temporary AWS credentials — without storing long-lived AWS access keys on the machine.

The idea

AWS IAM roles are a convenient way to give workloads temporary credentials. Inside AWS, services such as EC2 can obtain role credentials through AWS-native identity mechanisms. But a server outside AWS — a homelab VM, on-prem server, container host, or another environment — does not have an EC2 instance profile.

IAM Roles Anywhere extends the same temporary-role model to workloads outside AWS. The workload proves its identity with an X.509 certificate and its corresponding private key. IAM Roles Anywhere validates the certificate chain, authorizes the requested IAM role, and returns temporary AWS credentials.

Debian VM outside AWS
X.509 certificate + private key
↓ authenticate
IAM Roles Anywhere
Validate certificate, trust chain, and role trust
↓ issue temporary credentials
IAM Role
Normal IAM permissions determine what the workload can access
↓
AWS APIs
SSM Parameter Store, S3, DynamoDB, etc.

The mental model

Authentication Trust Anchor AWS trusts a configured CA certificate. A workload certificate must chain to that CA.
Authorization IAM Role The role defines the AWS permissions available to the workload.
Session Profile The profile selects the role(s) and can optionally apply session policies that further restrict the permissions of the resulting session.
Remember: the certificate says who the workload is, the private key proves possession of that identity, and the IAM role says what that identity is allowed to do.

Practical setup

1. Create a private CA

For a homelab, create a dedicated private CA for workload identities. In this example the CA is named IAM Workload CA.

The CA is the root of trust for workload certificates. Do not use a public certificate such as a Let's Encrypt server certificate as the Roles Anywhere trust anchor. AWS documents that certificates issued by public CAs cannot be used as trust anchors.

In this lab, the CA was created with pfSense's Certificate Manager.

2. Issue a workload certificate

Create an end-entity certificate for the workload. Example:

  • Subject / CN: dev
  • Issuer: IAM Workload CA
  • CA: FALSE
  • Key usage: Digital Signature
  • Extended key usage: Client Authentication

The private key stays on the workload. Only the certificate and its public information need to participate in the authentication exchange.

3. Create the IAM Roles Anywhere trust anchor

In AWS:

  1. Open IAM Roles Anywhere.
  2. Choose Create a trust anchor.
  3. Choose External certificate bundle.
  4. Upload/paste the PEM-encoded CA certificate.
  5. Create the trust anchor.

The trust anchor establishes the trust relationship between IAM Roles Anywhere and your external PKI.

4. Create the IAM role

Create a normal IAM role. This is the role whose permissions the workload will receive through temporary credentials.

The role's trust policy must allow the IAM Roles Anywhere service principal: 

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "rolesanywhere.amazonaws.com"
      },
      "Action": [
        "sts:AssumeRole",
        "sts:TagSession",
        "sts:SetSourceIdentity"
      ],
      "Condition": {
        "ArnEquals": {
          "aws:SourceArn":
            "arn:aws:rolesanywhere:REGION:ACCOUNT_ID:trust-anchor/TRUST_ANCHOR_ID"
        },
        "StringEquals": {
          "aws:PrincipalTag/x509Subject/CN": "dev",
          "aws:PrincipalTag/x509Issuer/CN": "IAM Workload CA"
        }
      }
    }
  ]
}
Important: scope the role trust policy. Without appropriate conditions, certificates from a trusted CA may be able to assume the role. Conditions based on certificate attributes help restrict which identities can assume which roles.

5. Give the role application permissions

Keep the actual resource permissions on the IAM role. For example, a development workload might only need access to its own SSM Parameter Store path: 

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "ssm:GetParameter",
      "Resource":
        "arn:aws:ssm:us-west-2:ACCOUNT_ID:parameter/myapp/dev/*"
    }
  ]
}

The role is the main authorization boundary. Start with least privilege rather than giving the workload broad AWS permissions.

6. Create a Roles Anywhere profile

Create a profile and select the IAM role created above.

A profile can also contain a session policy. A session policy does not grant additional permissions; it can only further restrict the permissions available in the role session.

During initial testing, a session policy of Allow * / Resource * effectively places no additional restriction on the role. Once the role is least-privileged, a narrower session policy can be used as an additional guardrail.

7. Install the Roles Anywhere credential helper

AWS provides aws_signing_helper. The helper uses the workload certificate and private key to authenticate and obtain temporary credentials. 

/usr/local/bin/aws_signing_helper credential-process \
  --certificate /etc/iamra/dev-roles-anywhere.crt \
  --private-key /etc/iamra/dev-roles-anywhere.key \
  --trust-anchor-arn arn:aws:rolesanywhere:REGION:ACCOUNT_ID:trust-anchor/TRUST_ANCHOR_ID \
  --profile-arn arn:aws:rolesanywhere:REGION:ACCOUNT_ID:profile/PROFILE_ID \
  --role-arn arn:aws:iam::ACCOUNT_ID:role/HomelabDevRole \
  --region us-west-2

The helper returns short-lived AWS credentials in the format expected by AWS's credential_process.

8. Configure AWS CLI

Configure a named AWS CLI profile. The entire credential_process command should be on one line in the AWS config file; shell-style line continuations do not apply there. 

[profile homelab-dev]
region = us-west-2
credential_process = /usr/local/bin/aws_signing_helper credential-process --certificate /etc/iamra/dev-roles-anywhere.crt --private-key /etc/iamra/dev-roles-anywhere.key --trust-anchor-arn arn:aws:rolesanywhere:REGION:ACCOUNT_ID:trust-anchor/TRUST_ANCHOR_ID --profile-arn arn:aws:rolesanywhere:REGION:ACCOUNT_ID:profile/PROFILE_ID --role-arn arn:aws:iam::ACCOUNT_ID:role/HomelabDevRole --region us-west-2

9. Test the identity

AWS_PROFILE=homelab-dev aws sts get-caller-identity

If successful, AWS has accepted the certificate, validated the trust chain, authorized the Roles Anywhere session, and returned temporary credentials for the IAM role.

Then test the actual resource permission:

AWS_PROFILE=homelab-dev \
  aws ssm get-parameter \
  --name /myapp/dev/test \
  --with-decryption

What happens during authentication?

  1. The workload sends a Roles Anywhere CreateSession request.
  2. The request is cryptographically signed using the private key corresponding to its X.509 certificate.
  3. AWS verifies the signature against the certificate's public key.
  4. AWS validates that the certificate chains to a configured trust anchor.
  5. AWS evaluates the target IAM role's trust policy and certificate attributes.
  6. Roles Anywhere obtains a session for the permitted IAM role.
  7. The workload receives temporary AWS credentials.
Certificate: "I am dev"
+
Private key: "I possess the key belonging to this certificate"
+
Trust Anchor: "I trust the CA that issued this certificate"
+
Role trust policy: "This identity may assume this role"

Security model

Component Question it answers
CA / Trust Anchor Which certificate authority do I trust?
Certificate Which workload identity was issued by that CA?
Private key Does the workload actually possess the private key corresponding to the certificate?
Role trust policy Is this authenticated identity allowed to assume this particular role?
IAM role permissions What AWS resources and actions can the role access?
Profile session policy Should this particular Roles Anywhere session be restricted further?
Most important security property: the Debian VM does not need a long-lived AWS access key and secret key. It proves possession of its private key, receives temporary AWS credentials, and uses those credentials to call AWS.

           HomelabStageRole
                 │
                 └── ssm:GetParameter
                     /myapp/stage/*

This gives each environment its own workload identity and IAM authorization boundary instead of sharing one AWS credential across environments.

What this enables

In the homelab deployment system, the Dev VM can use Roles Anywhere to retrieve application secrets from Parameter Store without storing long-lived AWS keys. 

Gitea Runner
    │
    │ Ansible / SSH
    ▼
Dev VM
    │
    ├── AWS credential_process
    │       │
    │       └── IAM Roles Anywhere
    │               │
    │               └── temporary AWS credentials
    │
    ├── SSM GetParameter
    │       ↓
    │   /myapp/dev/*
    │
    ├── write secret file
    │
    ├── docker compose pull
    │
    └── docker compose up -d

The application container itself does not need AWS credentials in this design. The host retrieves the secret and mounts the resulting secret file into the container read-only.

Setup checklist

  • Create a dedicated private CA for workload identity.
  • Issue an end-entity certificate for the workload.
  • Create an external-CA trust anchor in IAM Roles Anywhere.
  • Create an IAM role with a tightly scoped trust policy.
  • Attach least-privilege resource permissions to the role.
  • Create a Roles Anywhere profile and associate the role.
  • Optionally configure a session policy as an additional restriction.
  • Install the AWS Roles Anywhere credential helper.
  • Protect the certificate's private key on the workload.
  • Configure AWS CLI credential_process.
  • Verify with aws sts get-caller-identity.
  • Test the actual AWS resource permission.
